# WarmHouse System

# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут включать и выключать отопление, устанавливать желаемую температуру.
- Система поддерживает обновление текущего состояния устройства (вкл/выкл, целевая температура, текущая температура) самим устройством

**Мониторинг температуры:**

- Пользователи могут узнать текущую температуру и последнее время её обновления

### 2. Анализ архитектуры монолитного приложения

Текущая система реализована на Java с использованием СУБД PostgreSQL и Java Persistence API

В приложении есть закладка под отдельный `TemperatureSensorRepository`, но он в текущей реализации нигде не используется.

База данных состоит из двух таблиц `heating_systems` и `temperature_sensors`, содержащих информацию об устройствах отопления и датчиках температуры соответственно.

Приложение представляет из себя монолит, в котором сервисы управления и мониторинга делят одно адресное пространство и поэтому связаны напрямую.

Реализовано следующее API:
- `GET /{id}` - получение состояния устройства отопления `{id}`
- `PUT /{id}` - обновление состояния устройства отопления `{id}`
- `POST /{id}/turn-on` - включение устройства отопления `{id}`
- `POST /{id}/turn-off` - выключение устройства отопления `{id}`
- `POST /{id}/set-temperature` - выставление желаемой/целевой температуры для устройства `{id}`
- `GET /{id}/current-temperature` - получение текущей температуры `{id}`

### **4. Проблемы монолитного решения**

- При добавлении большого количества новых пользователей и их устройств, вероятно, захочется масштабировать некоторые части сервиса, в особенности те, которые в реальном времени обрабатывают значения с датчиков, а так же те, которые будут формировать по ним актуальную статистику. На данный же момент приложение масштабируется лишь целиком, что приведёт к неэкономному расходованию серверных ресурсов, а так же к задержкам в работе всего сервиса в несвязанных с обработкой данных сценариях использования.
- С учётом требования разброса клиентов по разным регионам, при масштабировании было бы целесообразно сервисы, связанные с обработкой данных устройств, поместить как можно ближе к пользователю, чтобы обеспечить отзывчивость системы.
- Монолитное решение не позволяет в моменты высоких нагрузкок временно увеличивать количество узлов, отвечающих за перегруженные части сервиса. Например, когда все пользователи одного региона возвращаются домой с работы в примерно одно и то же время, могут потребоваться дополнительные ресурсы для отработки пользовательских сценариев.
